## 1. 为什么做这件事

上一版开封三幕（桥、叠层、夜市）在模拟器上能完整跑通，但**它不是游戏**：每一幕都是把物件拖到唯一正确的位置，而正确答案已经写在说明文字里。没有信息差、没有代价、没有失败、没有第二局。

根因是选材：州桥「低平不通舟船，唯西河平船可过」在《东京梦华录》里写死了，玩家只能照答案摆。

本次换成有真实不确定性的环节——**考古探方**。玩家不知道地下有什么，要靠有限工日去换信息，再做判断。这才是玩法。

**定位变化**：原三幕降级为「档案导读」，不再是通关主线，不要删除。探方是开封的主玩法。

**设计红线**：

1. 奖励的是「判断对不对」，不是「挖到宝物」。不做文物收集、不做宝物价值、不做挖宝反馈。
2. 不靠虚构史实制造难度。难度来自玩家自己的信息不足，不来自编造的年代或器物。
3. 证据文案只用通用类别（淤土、砖瓦、石块、石壁残块、瓷片、扰土），并标注「探方布局为原创示意，不是州桥实测」。
   不允许出现窑口、具体年号、具体器型、人物姓名。确需写，先补来源再写。

## 3. 玩法规格（以此为准，不要自行加机制）

### 3.1 一局流程

1. 进入「汴河探方」，看到 5 列 × 4 行共 **20 个探方格**，全部覆盖。
2. 顶部常驻：**工日 10**、本局编号、当前已挖格数。
3. 玩家做两种动作：
   - **发掘**（点按某一格）：花 **1 工日**，揭示该格上层证据。
   - **下挖**（点按已揭示的格）：花 **2 工日**，揭示该格下层证据；没有下层时按钮禁用并说明。
4. 任何时候可以提交判断，工日耗尽自动进入提交。
5. 提交两项：
   - **必答**：桥轴在哪一列（5 选 1）。
   - **选答**：该列是「明桥压宋基」还是「仅见明桥」。
6. 结算：评级 + 依据回放（哪些格支持/反驳了玩家的判断）+ 可重开一局。
7. 重开换新种子，**成绩只记最佳与最近一次**，不做累计分数排行榜。

### 3.2 隐藏布局（每局由种子生成）

- 桥轴为 5 列中的**一整列**，均匀随机。同一列 4 格都属于桥位。
- 桥位格的上层证据固定为「石壁残块 / 桥面板石」，下层证据按本局类型给出。
- 非桥位格：上层从「淤土」「砖瓦」「瓷片」「扰土」中按权重取，权重在领域层写成常量表，不散落在 UI。
- 本局类型两种：
  - **叠压型（约 70%）**：桥位格下层为「更早的桥基石块」。
  - **单层型（约 30%）**：桥位格无下层，下挖直接提示「已到底，未见更早桥基」。
- 非桥位格一律无下层。

> 这样两类局都能被证据证明：叠压型要挖到下层才敢选「明桥压宋基」；单层型不下挖就答叠压，是猜，会扣分。

### 3.3 评级

| 评级 | 条件 |
|---|---|
| 甲 | 桥列正确 + 叠压判断正确 + 用工 ≤ 6 |
| 乙 | 桥列正确 + 叠压判断正确 |
| 丙 | 仅桥列正确 |
| 未过 | 桥列错误 |

- 选答留空按「未判断」处理：最高只能到丙。
- 结算必须显示**依据**：列出玩家挖过的桥位格与非桥位格数量，以及是否见过下层证据。不要只给一个字。

### 3.4 种子与可重玩

- 领域层提供字符串散列 + mulberry32，**不调用 `Math.random()`**，保证同种子同布局、可写断言。
- 种子 = `hash(chapterId + ':' + attempt)`，`attempt` 从 1 开始，存在记录里。
- 重开 = `attempt + 1`。杀进程、换设备后用同一 `attempt` 必须还原同一布局。

## 4. 数据与同步

新增一条进度记录，**不改已有 `progress:kaifeng-city:v1:*` 的格式**。

- 记录 id：`progress:kaifeng-dig:v1:roam-kf-night`
- `kind = 'progress'`，`siteId = 'roam-kf-night'`
- `body` 为 `KaifengDigV1` JSON，序列化上限 **1800 字符**（与城市记录同一量级）。
- 走现有 `copySnapshot` → `putRecord` → `commit` 链路，冲突仍按 LWW。
- 游客转账号的复制过滤要加入 `progress:kaifeng-dig:` 前缀（参照 `Index.ets` 里 `progress:kaifeng-city:` 的写法）。

字段建议：

```json
{
  "version": 1,
  "chapterId": "roam-kf-night",
  "attempt": 3,
  "phase": "playing",
  "workLeft": 6,
  "dug": { "0-2": 1, "2-1": 2 },
  "answerColumn": -1,
  "answerLayered": "unknown",
  "bestGrade": "",
  "lastGrade": "",
  "updatedAt": 0
}
```

- `dug` 的 key 为 `列-行`，value：`0` 未挖（不必存）、`1` 已见上层、`2` 已见下层。只存已挖格，控制体积。
- `phase`：`playing` / `settled`。
- 合并规则：同 `attempt` 取 `updatedAt` 较新者；`attempt` 不同取较大者，但 `bestGrade` 按 甲>乙>丙>未过>空 取较高。
- **写前合并**，参照 `Index.ets` 的 `saveKaifengCity`：先 `kaifengDigFromRecords` 取本地，再 merge，再写。
- 落盘时机：每次发掘/下挖、提交、重开。**不要在拖动或动画帧里写**。
- 解析必须严格：版本不符、字段缺失、格子越界、`workLeft` 非整数或与 `dug` 不一致，一律返回 `undefined`，不要补成「看起来正常」的存档。

## 5. 界面与交互

复用现有纸页坐标约定：**1000×2000 逻辑纸页**，等比缩放居中，绘制与热区共用 `unit()/px()/py()`。

- 探方区：5 列 × 4 行，格边长约 150 逻辑单位，整体放在纸页上半部。
- **点按，不要拖拽**。探方不需要 `rotate`，因此不会遇到上一版桥手势的坐标系问题；若后续加旋转，必须先读那份走查清单。
- 热区就是格子本身，不要额外放 120vp 透明方块互相覆盖。
- 底部信息：当前格证据、下挖按钮、提交按钮、工日。提交用独立按钮，不要做成滑条。
- 结算页用半模态，含评级、依据、重开。
- **布局硬约束**：底部面板会随内容长高（实测最高到屏幕 y≈1928）。探方格、提交按钮、工日都必须稳定露在面板之上；不允许出现「挖完了但按钮被面板盖住」。
- 空态与禁用态：工日不足时下挖禁用并说明；未挖格不能下挖；未选桥列时提交禁用。

无障碍 id（测试与走查都靠它）：
`dig-cell-<列>-<行>`、`dig-deep-<列>-<行>`、`dig-submit`、`dig-column-<0..4>`、`dig-layered-yes`、`dig-layered-no`、`dig-restart`、`dig-grade`、`dig-work-left`。

## 7. 必须写的断言（少于这个数不算完成）

1. 同种子同布局；不同 `attempt` 布局不同。
2. 桥轴恰好一列、4 格；非桥位格永不出桥位证据。
3. 单层型桥位格无下层；叠压型有下层。
4. 发掘扣 1 工日、下挖扣 2 工日；重复发掘不重复扣。
5. 工日不足时下挖被拒绝且不改变状态。
6. 未挖格不能下挖。
7. 工日为 0 时自动进入提交。
8. 桥列错误 → 未过；仅桥列对 → 丙；两项对 → 乙；两项对且用工 ≤ 6 → 甲。
9. 选答留空时最高丙。
10. 单层局不挖下层就答「明桥压宋基」→ 判错。
11. codec 往返一致；残缺/越界/版本错误的 body 返回 `undefined`。
12. merge：不同 `attempt` 取大者，`bestGrade` 取高者不被覆盖。
13. 记录 id 合法，`chapterId` 非法时抛错（与城市记录一致）。
