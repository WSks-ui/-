# 《汴京开市》：经营机制、文化依据与验证边界

调研日期：2026-10-25。目标环境：HarmonyOS 7 / API 26 原生 ArkTS / ArkUI。本文承接用户对“纸上生城没有明显游戏性、划剪与移光卡顿”的反馈。用户明确选择“有策略和反馈的经营模拟：安排资源，让文化场景运转起来”。

本轮先交付一个开封经营样板，不把同一种未经过真人认可的玩法铺到五城。原五城纸景、22条档案、旧记忆、AI两对象及个人长卷保留访问路径。功能通过只说明实现符合规则，不能据此宣称游戏已经有趣。

## 1. 玩家究竟在决定什么

玩家拥有六处沿河铺位、六名伙计、60游戏钱和起始食材。每段公开下一批客人的入口、食物偏好及夜间影响；玩家可以建铺、拆铺、调动伙计、安排街区灯火和选择两趟补货。确认开市后，一次结清真实客流与账目，再只读回放每位客人的结果。

- 开铺有一次成本，空着的伙计不自动接客；同一批人要在不同食物需求间安排。
- 补货每段只有两趟，缺米、肉、茶与缺灯油不能一次全部解决。
- 把铺子都挤在中街会消耗狭窄街区的通行能力；把铺子分到入口附近可以改变流失。
- 前两段不因未留灯减速，留灯仍耗油；后两段途经暗街和铺位本身都会受影响。灯油不足按公开规则先保中街，再西街、东街。
- 客流从水饭偏重转向夜深茶饮；提前备货和转移伙计会改变结果。
- 四段共100客，接待至少65客且余钱至少20为当前小样目标。价格、配额、阈值、容量均为原创规则，可在真人试玩后调整，不能解释成历史数字。

结算必须说明缺货、忙不过来、拥挤、街暗和未开对应铺子各流失多少客。原生场景的动画只消费本次真实 `visits`，不随机生成看起来热闹的经营成果；动画没有经济与存储副作用。新局不会生成个人手账，只有玩家确认自己的文字才新建普通note。

## 3. 卡顿的具体原因和本轮改法

旧纸景在每个move重放整笔，重复拷贝历史并做连通判断；移光又重建纸面边界、城市曲线和纤维。连续输入越长，重复工作越多。

新路径把真实输入保留完整，每帧仅盖印尚未处理的线段；最多排一个待绘任务。临时连通预览最多约96ms更新，抬手由原纯领域动作做一次正式提交。背景与城市素材按实际vp尺寸缓存，轮廓按mask/折法缓存；移光只刷新动态层。取消、隐藏和销毁释放排程与ImageBitmap。

主机探针比较的是计算与Canvas命令发出，不是原生GPU帧率。设备上的 `PAPER_SCENE_PERF` 同样只报告输入合帧、绘制命令CPU时间、缓存重建和预览/正式mask一致性，不能把它叫作触摸到显示延迟或60FPS证据。是否跟手仍需目标设备亲手操作。

## 4. 原生能力与当前验收口径

本轮经营使用原生Navigation、Canvas、透明原生铺位按钮及半模态资料/补货/账本。双Canvas把静态街市与逐客回放分开；后台、被遮挡及系统减少动态偏好停止或跳过动画。不是网页或鸿蒙专有渲染引擎。

2026-10-25实际核对本机API26 SDK：`ets/component/canvas.d.ts`中的`Path2D`、`ImageBitmap.close()`、`OffscreenCanvasRenderingContext2D`、`OffscreenCanvas.getContext()`及`transferToImageBitmap()`；`ets/component/common.d.ts`中的`SheetKeyboardAvoidMode`说明了RESIZE_ONLY与TRANSLATE_AND_RESIZE。声明存在只用于选择可编译接口；真正的离屏缓存CPU成本与平板键盘行为仍以本轮设备运行结果为准。API26不等同于已验收OpenHarmony API12兼容，也没有把这些普通ArkUI绘制接口宣传为新增鸿蒙可信跨端能力。

进度沿用schema v1的独立 `progress:river-market:v1:kaifeng`，经既有确定性版本比较与自建账号HTTPS通道同步；经营库存必须作为完整状态取一个版本，禁止两端累加。普通note只冻结确认时的文字、短引、来源与原创经营结果。旧pose、AI依据、纸景上下文和墓碑没有被迁移成经营数据。
