# 云河纪：核心玩法重构交接

更新日期：2026-10-23。**本文件优先于“只做前端美化”的任务描述。** 用户本次明确要求先修正交接、明确玩法重构方向，交给下一轮开发；本次没有实现下面的新玩法，也没有把它们登记为已验证的创新。

## 1. 先纠正对当前版本的判断

用户原本要求的是有惊喜的游戏化交互创新。当前已验收的五城版本完成了文化内容、原生页面、数据保存和同账号延续，但**核心体验仍更接近交互导览，不能据此宣称玩法创新已完成**。上一份前端交接把重点放到精美度和功能可感知性上，优先级偏了。

本次重新读了当前代码，问题有明确实现依据：

| 当前实现                        | 用户实际需要做什么           | 为什么还不足                         |
| --------------------------- | ------------------- | ------------------------------ |
| `RoamingChapterPage.move()` | 把一个`amount`从0拖到一定范围 | 大部分是展示进度，缺少可选择的解法和尝试结果         |
| `interactionReady()`        | 达到72、98等阈值，或曾经过观察区  | 完成条件主要判断“动过没有”，很少判断用户是否建立了文化关系 |
| `choose()`与`canConfirm()`   | 任选一个片段，然后确认         | 个人偏好选择成立，但它本身不构成解谜或创造玩法        |
| `feedback()`                | 没到阈值继续拖，达到后显示解释     | 缺少针对不同错误尝试的具体反馈，试错难以帮助理解       |
| 许多第三条线索                     | 选项改变尾页；开封另点亮灯       | 结果变化较少，前两步对结尾影响有限              |
| 选摘、UDMF、桌面卡片、分享             | 记录、拖入、继续和传播         | 是有用的原生能力，不能替代核心玩法规则            |

以上判断针对当前代码机制，不是新一轮真人研究结论。当前工作区在M12历史验收后另有前端调整，不能把眼下源码或新截图直接标成M12；保留他人已有修改，不回滚重做。

下一轮的首要任务应改为：**让文化知识成为操作和判断的依据，让玩家通过可尝试的规则改变故事，再留下由其操作产生的个人结果。** 换色、加动画、换卡片形状、加成就或积分不能单独算作本轮达成。

## 2. 作品的核心玩法方向

建议&#x4EE5;**“把文化关系亲手拼出来”**&#x4F5C;为可体验的主张。用户扮演的是在纸页中寻找关系的个人漫游者，不是文物修复专家或城市治理者。

每段至少形成一个闭环：

**观察线索 → 提出一个想法 → 直接操作场景 → 看见有原因的结果 → 调整或保留方案 → 展开下一段故事。**

必须具备以下五件事：

1. **具体目标。** “让街上的人和河上的船都能通过这座桥”，比“拖动看看州桥”更明确。
2. **有意义的操作自由。** 可以摆放、转向、叠合或改变结构，不能只有从左到右的单一进度条。
3. **可解释的尝试结果。** 有些尝试未成立，画面告诉用户哪个关系断了；允许撤回和再试。
4. **资料能帮助判断。** 读到“御街与汴河交会”，能改变下一次操作；文化不能仅在通关后作为附加知识卡出现。
5. **操作留下不同结果。** 玩家形成的构图、选中的依据或原创作品进入结尾，而非所有人只得到同一张已完成图。

不要求每个环节都制造失败。解谜环节要有规则，创作环节可以没有唯一答案；个人感想仍由用户决定是否保存。也不需要限时、排行榜、体力、签到和惩罚。

**差异化设计是待验证假设。** 以下方案借鉴空间解谜和可触摸机关的成熟思想，不能宣传为行业首创；必须先做原生样板，通过试玩判断是否真正有趣。

## 3. 第一条样板：开封“叠城寻路”

选开封是因为已有桥、街、河、城市层次与灯事材料，能够把一个问题拆成连续的操作链。工作名为“叠城寻路”；它是原创纸页叙事，不是历史城市复原或真实交通模拟。

开场不先摆三张任务卡。进入一幅尚未连通的纸页，能看见水上的船、街边的人和一座还没放好的桥，提出一句问题：

> 同一座桥，怎样让街上的人和河里的船都走得通？

### 第一段：把桥放到关系成立的位置

画面中有清楚标识的河、街、可移动的桥片。河与街的位置由关卡给出，玩家拖动桥片、调整方向；两个候选交会位置中，只有一个同时联系河道与街路。不是照着发光轮廓放零件，也不提前展示唯一答案。

玩家点“试着通行”后，系统根据当前摆放分别检查：

- 桥两端是否接上街路；
- 桥身是否跨过河道，而非顺着河道摆放；
- 原创示意中的桥下水路是否连通。

**结果来自当前结构判断，不是播放预先安排的成功动画。** 路未接上，行人走到缺口停下；水路不通，船停在断点。断点在画面上提示，文案说“桥连到了岸，但还没有接上街”，不只说“错误，再试一次”。

关系成立时，人从桥上过、船从桥下过；两条路径同时可见，然后展开一句短解释及出处入口。这里的创作数值、容差、运动速度只是玩法参数，不标成历史桥梁尺度或水工结论。

玩家无需先读长文。提示逐级提供“看看街通向哪里”→突出相关线索→在用户主动求助时演示一次摆放；演示不伪称玩家独立解出。小屏必须可单指完成，双指旋转只作可选增强，不以多指熟练度为门槛。

### 第二段：用同一处遗存联系不同时期

第一段成立后，不跳转到另一张无关卡片，而是在同一个桥位展开资料纸片：宋代桥基线索、后建桥体关系与今日考古观察。玩家拖动半透明资料片进行叠合，找共同锚点，并选择哪份依据能解释“这里不是只有一座同时代的桥”。

目标是理解“同一位置的不同时间”，不是按漂亮图案拼一张全景。初版只做有材料支持的一组前后关系，不擅自画出全城地层或三维地下城市。

- 位置对得上、材料关系也能解释，桥位留下双层轮廓和各自年代标识。
- 放入无关位置的材料，画面显示锚点无法对齐，可取回替换。
- 把两个年代当成同一时刻，保留两份纸片并提示“它们在同一处，但不在同一年”，由用户继续调整。

具体怎样形成锚点、需要几片、能否旋转，应由首个可玩原型收敛。禁止只把旧滑条换成透明遮罩，最终仍以“拖到72%”判定完成。

### 第三段：做出自己的灯，回到刚才那座桥

把前面“找到的关系”转成结尾作品。用户组合**原创**灯的骨架轮廓、纸面/纹样和一句祝愿，先看到灯的平面展开与立体示意，再把它放到自己想照亮的纸页位置。不同位置改变局部照明和构图，前两段留下的桥/时间轮廓仍在。

创作环节没有“唯一正确审美”。若设置装配步骤，只能说明是原创纸灯模型的规则，不能把随意想出的流程称为“汴京灯笼张真实非遗工艺”。正式技艺体验另需准确工序资料。

北宋灯事与清末以来灯彩技艺必须分开标年代。最后的亮灯是用户作品的结果，不是多选一张祝愿卡后统一亮灯。允许换纸、换纹样、挪位置并比较；“留成纪念”与“写个人感想”分别确认。

### 样板中必须有的状态

| 状态     | 画面和操作              | 不应该发生            |
| ------ | ------------------ | ---------------- |
| 未尝试    | 有问题、可操作物与简短线索      | 预先摆好答案或自动播放通关    |
| 关系未成立  | 人/船在具体断点停下，可以调整    | 扣分羞辱、清空全部尝试、只弹红字 |
| 成立一部分  | 分别显示街路、水路哪个已接通     | 把部分成立直接写成完整探索完成  |
| 关系成立   | 双路径实际通行，短解释紧随出现    | 只盖章但画面关系没有变化     |
| 求助     | 用户主动展开逐级提示，可撤回继续   | 强制跳过或把演示计为独立解谜   |
| 进入下一段  | 同一桥位展开资料层，保留空间线索   | 每步都回列表再点一张新卡     |
| 创作完成   | 自己的灯与摆放进入尾页        | 所有选择只换一行祝愿文字     |
| 保存个人记忆 | 预览个人文字、文化依据与作品，再确认 | 把游戏评价或模板写成用户感想   |

## 4. 五城分别用什么机制

这是下一轮推荐的机制分工，不表示五套新玩法已经实现，也不要求一次把15条都改成大型关卡。每城先有一个能记住的核心动作，其余内容围绕它展开。

| 城市  | 核心动作候选              | 有意义的规则/创造空间                                                        | 应理解的文化关系                            |
| --- | ------------------- | ------------------------------------------------------------------ | ----------------------------------- |
| 三门峡 | **折、剪、展开**自己的纸窗花    | 折叠改变剪口的重复方式；先预想再剪，展开后可撤回比较，得到自己的图案                                 | 日常居住与表达愿望；原创纸艺实验不冒称非遗标准教学           |
| 洛阳  | **把赏花短句放回人的生活场景**   | 围绕已核实短引做小型空间叙事：移动花影、窗框和人物位置，比较“看花/相聚”的不同画面；组合后要产生构图关系，不能仅拖到任意槽位即完成 | 赏花记述中的生活语境；不重排原文伪造诗句，也不混合不同时代为同一天   |
| 郑州  | **沿水与人的线索选路**       | 原创小景有可回退的分岔；所发现的水名、地景与交往线索改变后续可达路径；选择不同路线会遇见不同片段                   | 《溱洧》的水名和人际交往；路线为叙事设计，不称古城真实街图       |
| 开封  | **叠合资料、接通两条路径，再制灯** | 多个操作变量、局部成立与错误反馈，前后步骤在同一场景产生因果                                     | 州桥联系街河、同址多期、节俗与技艺年代区别               |
| 濮阳  | **用可移动侧光/观察窗读线索**   | 改变观察方式显出不同轮廓；将看到的具体证据与考古/传说/民俗的解释建立联系，完成自己的证据纸页                    | 不同材料如何支持不同结论；不能把光照生成的示意纹理称为真实遗物隐藏信息 |

洛阳、濮阳的操作规则仍需原型推敲；如果试玩后仍是“动一下→读卡片”，就不能算完成。不要为了五城数量，再复制同一套阈值滑条并换背景。

## 5. 鸿蒙能力怎样进入玩法

**创新主张属于“文化与操作规则的结合”，原生能力负责把它做得自然。** 不把常见系统API的接入数量当作核心创新证据。

| 能力                            | 应服务的具体动作                             | 验证边界                                   |
| ----------------------------- | ------------------------------------ | -------------------------------------- |
| ArkUI Pan/Rotation/Pinch与手势组合 | 桥片移动、角度调整、资料叠合、细节观察                  | 本机API26声明存在；新关卡手势冲突、坐标和可操作性仍须原生验证      |
| 原生Canvas与状态动画                 | 当前摆放决定路径、断点、纸张变化和照明结果                | Canvas已使用；新路径判定不能被动画时长替代               |
| UDMF系统拖拽                      | 平板将**有身份的证据卡**拖入资料叠合区域，用于推理；不是只拖到笔记框 | 旧摘录拖放通过，不等于新“证据入场景”路径已经通过；校验来源与引用      |
| SelectionContainer            | 从资料主动选摘为证据卡                          | 仍是先生成卡，再拖卡；不承诺选中的原文本身可直接拖              |
| 响应式布局与原生Sheet                 | 手机单场景聚焦，平板资料与操作相邻                    | 按真实内容宽度；不把所有资料做成工作台，不让输入遮住操作           |
| 触觉反馈（可选）                      | 合法吸附、关系接通时给短反馈                       | SDK有接口及能力/权限失败；模拟器触觉不可感知，不把它当现成亮点或验收门槛 |
| 同账号HTTPS                      | 在自己的另一台设备继续真实进度/作品                   | 当前通道真实可用；新半成品格式和续玩位置需单独验证，不能写成原生可信接续   |
| ShareKit / FormKit            | 分享亲手完成的作品，桌面继续自己的探索                  | 是结果出口；不代替游戏过程，不伪造对方收到或自动存笔记            |

不要为了显得像鸿蒙而强制摇晃、倾斜、吹气或要求两台设备同时在手。若以后有一个传感器能解决真实玩法问题，再核对设备与SDK；当前模拟器仍应能完整体验核心关卡。

## 6. 代码与数据怎么接，旧成果怎样保留

现有结构可作为底座，不重写账号与全应用导航：

- [RoamingChapterPage.ets](../entry/src/main/ets/components/RoamingChapterPage.ets)保留篇章编排、阅读/写作与保存回调，将新核心玩法分支交给独立组件；不要继续往一个`amount`里塞所有状态。
- 建议新建纯领域规则模块（例如`domain/KaifengPuzzle.ts`，**当前尚不存在**），分别表达桥位/方向、连接判断、尝试结果和提示状态。平台手势、Canvas、系统拖拽放在组件或`platform/`中。
- 建议新建关卡组件（例如`components/KaifengPuzzleScene.ets`，**当前尚不存在**）。输入用户状态，输出明确动作/解题结果；不直接写Preferences，不由画布定时器创建progress。
- [RoamingScene.ets](../entry/src/main/ets/components/RoamingScene.ets)仍承担既有图景。当前记忆预览按完成态绘制，不能声称已经保存了玩家的精确摆放或完整操作回放。
- [Roaming.ts](../entry/src/main/ets/domain/Roaming.ts)与[ArchiveDomain.ts](../entry/src/main/ets/domain/ArchiveDomain.ts)的现有schema v1、ID、墓碑、pose和AI冻结依据继续保留。旧通关记录仍按旧玩法解释，不抹掉，也不能改称“已解新版谜题”。

新关卡在最终成功并且落盘确认后，才显示完成；自由阅读、查看提示和动画结束都不是成功证据。旧`progress:roam:v1:*`不能用来掩盖新版规则没有执行；是否增加独立版本化玩法进度，应在实施前写明迁移/兼容方案，不能悄悄复用旧完成标记。

若要把桥位、灯形、纸纹或叠合状态保存成纪念，必须定义**独立版本化的作品/玩法上下文**，贯穿解析、深拷贝、比较、落盘、HTTPS及预览。不能只存在UI内存，也不能写进旧`snapshot3DPose`。旧记录没有的新字段保持缺省；不认识的图景修订应保留文字与出处并诚实提示，不能用新图冒充旧保存场景。

文化正文或图景解释如有变化，应推进相应修订并冻结新出处，旧记忆依据不重写。第一次样板可以只验证玩法状态，随后接入明确确认的纪念作品保存；最终交付必须清楚说明哪部分已经持久化、哪部分只是本次临时尝试。

## 8. 先交付什么，怎么判断真的变好了

### 首批交付

先把开封做成**有完整玩法闭环的一篇**：问题、操作、至少两种未成立反馈、成功表现、下一段关系、原创制灯与纪念预览。其余四城保留原入口与原内容，待样板好玩后再各做一种机制；不因计划覆盖五城而提前把五城新版玩法全标完成。

外观同步服务当前动作，但不能先把主要工作花在全站卡片换皮上。先交付可玩的原生样板，再做全应用视觉统一。

### 原生验收与真人试玩

1. **错误也要测。** 桥放岸边、顺河摆桥、只接通一端分别产生对应画面；未成立时不写完成记录。不能只录一条预定正确答案的自动演示。
2. **不能用旧阈值绕过。** 滑满、反复点确认、看完资料或触发动画结束均不能替代规则成立。
3. **操作与结果一致。** 改变桥位和方向确实改变通行；资料层不是固定视频；不同原创灯配置/位置留下可区分结果。
4. **文化解释有用。** 试玩者能说出为何这一次接通、资料指向什么关系，而不只是“拖到发光就成功”。
5. **提示能救场。** 玩家卡住可主动求助并继续，没有被强制清空或只能退出。
6. **作品确为自己的。** 已保存的结构在重新打开、横竖屏及当前HTTPS另一端恢复一致，冻结出处和旧记忆不受改写；未实现的恢复明确标待完成。
7. **首次无需账号。** 不登录、不请求AI可完成本机样板，动作中不出现技术工作台或账号门槛。

建议先找3—5名未看说明的人做短试玩，记录实际现象：是否发现第一步、是否形成一次有理由的调整、卡在哪里、能否解释文化关系、是否愿意保留作品。人数、用时、原话和是否看了提示要如实记录；这些是下一轮建议，不是已完成的研究，也不保证“惊艳”。

必要工程检查仍为`tools/test.ps1`、`tools/build.ps1`及对应原生定向测试。规则模块需要有意义的连接/未连接与保存兼容测试；不为低影响样式重复写镜像测试，不扩展生产治理。新包绑定、新截图与原始Pass/Failure/Error单独留存，M12历史结果不继承为新版通过。

验收报告要分开写：**功能已实现、原生操作已走通、真人是否理解/觉得有趣**。后两项没有证据时，不用“创新完成”替代。
