# 云河纪全面审查：比赛要求、产品体验与创新主线

审查日期：2026-10-20。基线提交：`9103246`。工程：HarmonyOS 7 / API 26 原生 ArkTS / ArkUI。

本报告依据本轮源码、目录清点、实际构建、服务测试和原生模拟器操作。历史验证只按原版本引用；界面截图来自设备，不使用网页原型代替运行结果。最终复核结果见文末“本轮验证”。

## 1. 结论

**云河纪已经有可以形成竞赛记忆点的完整体验，但当前版本尚不能判定全面满足赛题。**

最有价值的体验是：用户提出一个关于器物的具体问题，AI 根据限定资料解释，用户点击回答中的观察动作，原生画面聚焦真实热点，再把自己的理解和当时视角保存为手账，在同账号另一端重新打开。这条链路把文化内容、AI、原生交互和个人数据连在一起，值得成为答辩主线。

当前最影响成绩的缺口集中在三处：赛题指定的鸿蒙分布式数据服务与华为账号尚未接入；正式演示的服务地址与安装方式尚未完成；龙山与窑址两个规定检索维度没有内容命中。继续增加首页模块，不能解决这些缺口。

产品体验方面，新版记忆、档案与我的页比旧版完整，排序、标签、管理、统计和二级页面都已接通。新的问题是管理控件挤占内容，手账和文化发现出现得太晚；首页与档案仍重复提供完整目录检索，评委容易看到功能数量，却记不住核心价值。

本次不为作品预测名次或虚构评分。下面每项建议都对应可展示的结果或可复现的验收。

| 最新时间戳优先、最终一致性 | 算法与 HTTPS 路径已有 | 同时保留稳定并列裁决和删除墓碑；需在原生分布式传输路径重新验收 |
| 同步方向、进度、最后时间、冲突数可视化 | 部分满足 | 有状态、最后同步和设备/冲突计数；没有手机→平板方向、记录阶段、冲突历史查看 |
| 安装预置图文、离线阅读 | 基本满足 | 20 条正文与本地图片随包，静态目录不依赖网络 |

| 根据收藏与浏览智能关联推荐 | 已实现且页面有接入 | 详情最底部“继续探索”调用 `recommendSites`；不应再说算法没有落地。当前入口过深 |
| 自定义主题、个人知识网络 | 已实现基础功能 | 手账标签派生个人图谱与关联线；主题和关系通过现有账号记录间接同步，没有原生分布式验收 |

| 两端补充修改、合并与排序笔记 | 部分满足 | 按记录版本采用较新版本；界面排序是本地筛选状态，没有可同步的用户手动排序或结构化正文合并 |

## 4. 优先级最高的问题

### F01 / P0：鸿蒙分布式技术缺口

证据：`LocalArchiveRepository.ets` 使用 `preferences`；`SyncGateway.ts` 的分布式适配仍是 `UnavailableSyncGateway`；正式模块仅声明 INTERNET 权限；实际交换在 `AccountSyncClient.exchange()`。

影响：评委一旦追问“在哪里调用分布式数据库、设备如何发现、离线冲突如何在两台设备上验证”，当前无法给出题目要求的完整证据。

处理：沿用已完成的领域合并、墓碑和账号隔离，新增真实平台适配与数据迁移；两台受支持设备验收。**改类名、增加 KV 导入或在页面画手机→平板动画都不算完成。**

### F02 / P0：正式演示服务接入尚未成立

证据：`AccountSyncClient.configure()` 与 `WaterSituationClient.configure()` 在非 DEBUG 下直接返回 false；`validateServiceEndpoint()` 仅接受 HTTPS 回环/私有 IPv4 与四五位端口，拒绝公网域名。`build-profile.json5` 没有签名配置，当前主包为 unsigned。

影响：README 所说的“答辩前切换腾讯云 endpoint”不能通过只填公网地址完成。独立实机安装、AI、水情与账号网络访问都要按最终环境核对。

处理：先固定比赛使用的两台设备、局域网或公网服务路径、包模式与签名。若使用公网服务，补正式受信任 TLS 配置入口；若使用调试包与局域网，按该路径完整演示并在材料中写清。现有签名和证书不覆盖、不公开。

### F03 / P0：账号离线冷启动有缺口

证据：会话仅在 `AccountSyncClient` 内存中；应用冷启动读取游客仓库，认证成功后才进入账号专属仓库。

影响：用户在线使用后关闭应用，断网再打开，不能直接访问之前登录账号的离线手账。这会削弱题目强调的离线编辑体验；并不表示数据已被删除。

处理：保存可恢复的账号工作区身份，恢复本地数据访问；网络授权过期与本机可读状态分开。不得把游客档案与账号档案静默混在一起。验收用真实“已登录使用→关闭进程→服务不可达→冷启动→读改原手账→重连”路径。

### F04 / P0：规定维度有空档

证据：`ERAS` 含龙山、`TYPES` 含窑址，但本轮目录清点均为 0；筛选要求与 `era/type` 字段精确相等。

处理：补有出处且符合五城边界的真实条目，或为确有多期遗存的档案设计来源明确的检索分期。不能仅把一个现有仰韶遗址改标龙山来消除空结果。文化分类扩展不应改旧档案 ID、收藏引用或历史手账。

### F05 / P1：恢复能力缺少后半程

证据：我的页只有 `copyBackup()`；没有从文件导入、检查、合并、恢复和取消路径。备份扩展只保留生命周期日志。

处理：先提供可带走的备份文件，再提供恢复预览与合并。恢复保留目标设备身份、账号隔离与删除墓碑；恢复失败保持当前数据。完成后再宣传“一键恢复”。

### F06 / P1：同步面板的状态语义不完整

证据：冲突数来自服务端累计保留的落败版本，界面却显示“X 项待处理”；当前已按版本规则裁决，没有实际待处理列表。手账卡用 `lastSync >= updatedAt` 推断同步状态。

影响：累计冲突、待上传变更、远端确认和已到达另一端容易混为一谈。一次健康轮询不代表另一台设备已经落盘。

处理：面板展示实际设备方向、待发送/已发送/远端已确认等可观测阶段；累计冲突改称“已按较新版本合并，保留 X 条历史版本”，并接通查看。没有记录总量时不显示百分比。

### F07 / P1：推荐有实现，展示位置与解释仍弱

证据：`recommendSites` 根据收藏与浏览选锚点，同年代 +4、同城市 +3、同类型 +2、共同标签逐项加分；详情底部渲染前三个未收藏、未浏览候选。

问题：推荐在长正文、资料来源与手账之后；用户浏览全部 20 条后候选为 0，“继续探索”标题仍存在。随着浏览增多，取锚点最高匹配的排名也可能失去近期兴趣差异。

处理：在档案页提供紧凑的“下一处发现”，点开可看推荐原因；详情在完成观察或保存后给下一步。候选为空时显示回顾主题或当前已全部探索的真实提示。规则推荐属于算法能力，不包装成大模型推理。

### F08 / P1：跨端布局有实现，实际平板证据不足

证据：主页面有 840vp 阈值和 `NavigationMode.Split`，不是完全没做宽屏适配；当前已有验证设备均为同分辨率手机模拟器。

处理：用实际平板/折叠设备或对应镜像检查分栏、阅读宽度、编辑器、键盘与返回关系。答辩应展示“手机挑选与观察、平板展开资料与手账”的明确分工。同一套代码声明 tablet 不等于平板已验收。

### F09 / P1：学习与浏览的用词需要统一

证据：打开详情会写 `body: 'opened'` 的浏览记录；档案卡把这类状态显示为“已读”，其他页面用“已浏览”。四主题探索另有显式完成规则，简单打开并不完成任一主题。

处理：普通打开统一称“已浏览”；主题阅读显示真实 25% 步进或已探索主题数；路线点亮仍沿用 75% 或有效手账的现有规则。手账年月与“最近/最早”按 `updatedAt` 排列，应明确是更新时间，避免被理解为创建或实际到访时间。

### F10 / P2：数据页面向用户的表达与计量

证据：数据页直接写 Preferences、JSON，`storageKb()` 用 `JSON.stringify(...).length / 1024` 估算“本机占用”。字符串长度不是含中文 JSON 的 UTF-8 字节数，也不是 Preferences 的实际磁盘占用。

处理：面向用户显示“导出个人档案/恢复档案”，具体格式放次级说明；如果展示大小，计算真实备份字节数并标“备份文件大小”。不用估计的字符串长度宣称真实存储占用。

|---|---|---|---|

| 河迹首页 | 主题、AI、最近记忆、纸页入口、沙盘、水情、图谱、城市、完整检索 | 模块多且前后争夺注意，完整检索与档案页重复 | 首屏围绕一个具体文化问题；最近记忆与下一步紧邻；完整检索集中到档案页；保留用户已有纸面视觉 |
| 文化详情 | 三处独立观察、热点、事实、AI、收藏、笔记、图文、推荐 | 长页面串联过多层级；重要动作之间需要上下滚动 | 按观察、资料、我的记录组织；当前观察动作保持易达；来源可展开；保存后直接提示回放与下一处 |
| AI 观察 | 真模型、上下文、动作、依据、可编辑草稿、取消等待 | 只有两个对象；草稿仍需滚动；游客只有登录路径文字提示，缺直接返回对象的一键登录闭环 | 完善主线两件的操作连贯性；登录后返回原对象及问题；有价值的问答由用户明确保存 |
| 记忆 | 全文、编辑、回放、搜索、排序、标签、批量复制删除 | 首屏控件过多，第一条记忆出现过晚；写新手账还需绕到档案 | 默认展示内容，筛选/排序收进一个面板；管理态再展示批量操作；新建可选最近档案并明确将保存在哪一处 |
| 收藏 | 三种标签分类、搜索、收藏卡片 | 缺少主题视角的下一步，容易停留在书签列表 | 分组数与“继续观察/写手账”可见；不改变个人应用定位 |
| 档案 | 独立城市状态、多维筛选、已浏览与收藏范围、AI 入口、重置 | 顶部 AI 卡和多层筛选占内容；年代与类型的空档会被直接发现 | 做完整资源目录；添加有计数的年代浏览与一条可解释推荐；保持检索条件与结果强对应 |
| 文明图谱/对照 | 全部/个人、节点、主题、条目对照、器物三维度资料 | 同城、同年代、同标签连边较多，容易被理解为历史传承；用户难读出重点 | 默认突出一条当前线索；点击才展开依据；明确个人专题与历史证据的区别；时间关系必须有来源 |
| 我的 | 四格统计、主题漫游、账号数据、偏好、关于 | 统计与管理较多，个人“走过哪条文化线索”较弱 | 先给真实探索足迹、最近主题与下一站，再进入管理；保留已完成二级层级，接通真正恢复与同步历史 |
| 河窗水情 | 真实服务端适配、三站、缓存与离线回退 | 与个人文化记忆联系较弱；日报值的“实时”容易被理解为连续采样 | 作为辅助入口；标“最新观测 + 日期时刻/离线”；只在来源支持时连接州桥、水患等历史条目，不从水情自动推断遗址状态 |

### 5.1 记忆首屏的实际证据

本轮 AI 手账保存后的设备截图中，第一张卡片顶部在 **y=1972px**，Dock 从 **y=2529px** 开始，屏幕高 2760px。上方已依次出现标题统计、手账/收藏、搜索、AI/列表/画廊、排序、换行标签和月份。第一张卡片只剩约 557px 的可见空间，主要动作还在下方。

这是内容优先级问题。建议默认保留“手账/收藏 + 搜索/筛选入口”两层，把排序、AI 和全部标签放入筛选面板；在真实设备截图中验收第一张记忆的标题、正文摘要和主要动作能够同时出现。

原生画面见[记忆首屏](2026-10-20-assets/02-memory-first-screen.png)、[档案首屏](2026-10-20-assets/03-library.png)、[我的](2026-10-20-assets/05-profile.png)、[AI 聚焦](2026-10-20-assets/01-ai-focus.png)。这些图中的记录是独立测试档案；保留原始画面，没有用设计稿替换。

### 5.2 文物与遗址的实体关系

双连壶 AI 使用 `zz-dahecun`，个人手账和收藏也记在大河村条目。评委若询问“我收藏的是遗址还是那件文物”，需要清晰回答。后续可在详情中给文物独立对象卡并标所属遗址；如拆分独立 ID，必须保留旧记录映射与视角回放兼容，不能直接改旧 ID。

## 6. AI 应如何真正融入

### 6.1 当前应该主打的能力：能操作的有依据观察

推荐讲法：**“问一个问题，找到一个细节，留下一页可以重返的记忆。”**

它已经有四项相互支撑的实现：限定对象的事实集；可校验的部位动作；原生画面和实际相机；用户确认的手账及冻结依据。它的价值是帮助用户理解眼前的文化细节，而不只是提供一段回答。

优先完善方鼎和双连壶：两件各至少一条可连续操作的观察问法，支持追问、依据、草稿、保存与另一端回放。先完成这两件的稳定展示，再把有核实资料的庙底沟作为第三对象。

具体把两件作品做成两个能亲手发现的瞬间：

| 观察对象 | 评委参与的问题 | 画面要发生的变化 | 当前与下一步 |
|---|---|---|---|
| 杜岭二号方鼎 | “我只看到四组，另外四组在哪里？” | 从壁面正中转到折角，观察位置与依据同时对应 | 聚焦、依据与手账已实现；可进一步让评委先选观察位置，再由 AI 接着解释 |
| 大河村双连壶 | “两只壶口，为什么还是内部相通的一件器物？” | 聚焦腹部通口，清楚呈现双口与腹部连接关系 | 对象化问题与热点已实现；剖视或透视滑块属于待开发的原生学习示意，不能预先称已完成 |
| 保存后的同一页手账 | “换一台设备，还能回到刚刚的位置吗？” | B 端收到这次新增记录，恢复同一部位、角度与用户文字 | 现有 HTTPS 曾验收，本轮重新复核；原生分布式通道仍待完成 |

这三处变化都能让评委参与操作和核对。补充的动效应帮助看清部位与关系，不能把时间用于表演没有对应数据变化的同步动画。

### 6.2 适合新增的三个场景

| 场景 | 用户价值 | 可见交互 | 范围与约束 |
|---|---|---|---|
| 文明线索漫游 | 知道下一处为什么值得看 | 选“器物/都城/水与城市”等主题，展示三到四处真实档案与每段依据，点击即进入 | 本地算法选条目；AI 仅解释已提供关系，不凭标签宣称文化传承、技术演化或因果 |
| 手账重访 | 重新理解自己之前的观察 | 打开记忆时展示当时问题、事实与视角；用户选“继续这个问题”或“与另一件对照” | 只带入明确选中的手账；不默认上传整个个人库；新生成内容须确认保存 |
| 个人文化长卷 | 看见知识积累的结果 | 按城市/时期排列真实收藏和手账，点一个节点回到原画面；生成可编辑的主题短序 | 图谱与长卷由真实记录派生；AI 只整理已有笔记，不编造参观经历或学习成果 |

### 6.3 各页的 AI 角色

- 首页：给一个可立即参与的问题，不增加第二套聊天入口。
- 档案：从用户明确兴趣和已核资料中解释推荐；筛选事实仍由本地规则执行。
- 详情：解释当前对象、聚焦部位、查看依据，是主能力所在。
- 记忆：接着已保存的问题重访，把个人观察和资料依据区分展示。
- 我的：由真实记录生成个人文化足迹，生成文字由用户确认，不用模型制造完成度。

这些是下一阶段设计，不计入当前实现。AI 事实引用的结构校验并不自动保证全部语义正确，答辩不能宣传“零幻觉”。

## 7. 鸿蒙能力核验与实现边界

本轮核对本机 HarmonyOS SDK 26 的 `@ohos.data.distributedKVStore.d.ts`、`@ohos.data.distributedDataObject.d.ts`、设备管理与华为认证声明。

- SDK 有 `createKVManager`、`getKVStore`、`sync(deviceIds, mode)`、`dataChange` 与 `syncComplete` 等接口，可作为适配入口。
- `Options.autoSync` 声明要求分布式同步权限，并限定其生效场景。**不能假设设置 `autoSync: true` 后两台任意模拟器会自行发现、认证和同步。** 可信设备关系、权限、签名与设备能力要在选定环境分别核对。
- 当前工程有 HDS 与 HMS 依赖，`runtimeOS` 为 HarmonyOS，目标与兼容 API 都为 26。它与 OpenHarmony API >= 12 的对应关系必须按实际可运行能力说明，不以版本数字作等价证明。继续用户已经确认的团队自有设备路线，不把重新询问组委会设为前置步骤。
- 一次开发多端部署已有分栏代码，但仍需手机/平板原生画面证明。
- 当前 Canvas 几何是学习示意。没有授权扫描模型与设备 GPU 验收时，继续准确使用“原生交互观察”表述。

建议分布式实现沿用记录级信封与确定性合并。迁移应可核对记录数量、稳定 ID、标签、视角、AI 元数据与墓碑；不能把整个 JSON 快照简单放进一个可覆盖键，再假定离线并发天然正确。

官方核验入口：[分布式 KV](https://developer.huawei.com/consumer/cn/doc/harmonyos-references/js-apis-distributedkvstore)、[分布式数据对象](https://developer.huawei.com/consumer/cn/doc/harmonyos-references/js-apis-data-distributedobject)、[华为账号登录](https://developer.huawei.com/consumer/cn/doc/harmonyos-guides/account-phone-unionid-login)。本次接口结论来自本机 SDK 声明，不代表目标设备已通过该能力验收。

## 8. 内容、性能与工程判断

### 内容

现有 20 个官方来源页面可访问，是文档可信度的基础。建议优先建立每条档案的“事实—来源段落—核验日期”对应，再扩展目录；照片来源、署名和许可继续保留。程序化学习示意、馆方图片、个人观察与 AI 解释分别标明来源身份。

诗文不足应通过有出处的地域诗文解决，明确它与城市、河流或具体遗址的关系。文旅信息可以提供管理机构入口、地址和最近核对日期，无需虚构票价、预约名额或开放状态。

### 性能与稳定性

主包约 6.10 MiB，安装预置内容规模适合演示；本轮本地与服务测试通过。没有新增帧率、耗电、长时压力或大字体专项，不能据此宣称恒定 60fps 或低功耗。当前 20 条目录的首要问题是发现路径和控件密度，暂不需要为了生产规模重构整套列表。

AI 提问与草稿的本轮真实服务耗时分别为 1888ms、2205ms；这是两个请求的本次值，不是长期平均值，也不是整条演示耗时。

### 工程

领域层与平台层已分离，版本裁决、删除墓碑、损坏不清空和真实写入确认有基础。`Index.ets` 同时承担首页、记忆、档案、路由和账号编排，之后可逐页拆分；该重构不应挤占分布式、离线冷启动和主线体验的交付时间。

交接文档累积了大量历史“当前状态”。README、HANDOVER、TEST_REPORT 和 Word 应增加统一版本封面与能力矩阵，任何能力都注明“当前实现/当前包验收/下一阶段”，防止把旧包双端、当前 AI 与后续分布式混写。

## 9. 推荐的答辩主线

目标是让评委看见三个明确变化：**看懂一个文化细节、保存一次自己的发现、换设备回到同一处。**

| 目标预算 | 操作 | 屏幕必须给出的证据 |
|---|---|---|
| 0—20 秒 | 首页从“四面方鼎为什么有八组兽面纹”进入 | 文化问题与观察对象明确，不先讲菜单 |
| 20—65 秒 | 真实提问，点击“看四个折角”，展开一条依据 | 模型实际改变视角；事实和来源能打开 |
| 65—110 秒 | 输入一句个人观察，生成并确认手账 | 个人文字、实际视角和依据一同保存 |
| 110—150 秒 | 切换已登录同一账号的第二设备 | 收到刚新增的记录，预览、正文和部位对应，实际回放 |
| 150—180 秒 | 展示由真实记录变化的主题节点或下一处推荐 | 用户行为确实改变个人知识结构与下一步 |

这是计划预算，尚需真人计时。原生分布式完成后，主线的跨端段再使用该通道；当前 HTTPS 路径只能如实介绍为账号网络同步。

离线编辑、重新连接、冲突裁决与恢复适合答疑时额外演示，避免把三分钟主线扩成全部功能清单。准备同版本备用录像，展示真实先后关系，不用静态截图切换冒充同步。

## 10. 评委最可能追问的六件事

1. **“分布式在哪里？”** 当前事实是自建 HTTPS；完成后展示实际平台接口、设备关系、传输事件和 B 端落盘，不用架构图代替。
2. **“AI 比通用聊天多了什么？”** 展示对象资料约束、可操作部位、原地依据和可重返的手账；让评委自己换一个问法。
3. **“同时离线修改怎么办？”** 展示记录版本、时间戳、稳定并列裁决、删除墓碑和保留的落败版本，最终两端相同。
4. **“断网再打开还能看原来的笔记吗？”** 当前账号冷启动有缺口，必须补完后再演示这句话；游客资源离线阅读已具备。
5. **“推荐依据是什么？”** 展示本地规则与用户收藏/浏览产生的真实结果，不把标签相似当作历史传承。
6. **“照片、模型、诗词是真的吗？”** 出示条目来源和图片许可，解释学习示意范围，保留未校审状态。
